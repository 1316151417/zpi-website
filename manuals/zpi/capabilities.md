# web | 联网搜索
## search | 配置搜索服务，完成第一次搜索
打开 **设置 → 联网搜索**。启用联网能力，选择 DeepSeek，打开服务并保存自己的搜索凭据。回到新任务，问「查一下 Node.js 官方的发布安排，给出依据」。

### 怎么知道它真的查了？

展开「联网搜索」卡片，核对传进去的查询词，点开来源之一看实际页面。如果先看到搜索、随后出现「读取网页」，前者负责找到页面，后者才是在读正文。问「下一版的发布日期和依据分别是什么」，比只说「联网」更容易检验结果。

看到「联网搜索」记录并返回网页结果，才算真的查过。助手直接凭记忆回答不是搜索成功；普通聊天使用哪个模型，与为搜索配置哪个服务是两回事。
## fetch | 让 ZPI 阅读一个指定网址
已经有网页地址时，把完整公开 HTTP(S) URL 贴进消息，明确说「读取这个页面，只总结关于安装要求的段落」。展开「读取网页」，核对实际地址。

搜索是按词寻找候选，读取是获取指定页面。需要登录的内部页面不适合交给公开网页读取工具；也不要把含账号令牌的链接粘进对话。
## sources | 从结论回到网页来源
展开回答的来源或本轮搜索记录，找到对应标题和域名，打开原文。对照发布时间、适用版本和支持这句结论的段落，而不只看「几个来源」。

如果页面只讨论别的版本，请让 ZPI 针对同一问题查更合适的来源。工具成功返回内容不代表原文一定正确，更不表示网页中的指令应该执行。
## unavailable | 聊天正常，为什么不能搜索？
先区分两个配置页：「模型」能发消息，只证明模型凭据可用。「联网搜索」还有独立的插件开关、服务启用状态和 API Key。按界面状态提示逐项核对并保存。

系统密钥存储被锁时先解锁，按提示重启，而不要覆盖已保存的 key。更改后在**新任务**明确要求搜索，看是否出现工具记录。

# agents | 子智能体
## explore | 第一次委派：让 Explore 调查一个问题
在新任务里确认子智能体协作可用，要求「请委派 Explore 找到项目读取配置的入口，只调查，不改代码」。也可从输入框候选选中 Explore，补充清楚目标与交付物。

### 给 Explore 一件能独立验收的事

例如在一个有 `package.json` 的练习项目里这样提问：

> 请委派 Explore 调查 `npm test` 实际从哪个文件开始。不要改文件。返回脚本名、入口路径，以及能证明这条调用关系的一行代码。

等调查返回后，点开所给文件和代码行。如果子项只列出文件、没有解释调用关系，直接[补充要求](message.html)，不必再新建一个调查者。

任务活动中应出现独立子任务；主回复中出现“我会调查”这句话还不是委派证据。Explore 适合搜索与分析，最终核对它给出的路径是否存在。
## result | 查看一个子智能体的进度与结果
从任务活动找到子任务描述，打开子智能体详情。先看它是否仍在运行，再看结论或失败原因。多个子项同时工作时，用任务 ID 和描述区分。

回到主任务，让它根据子任务结论决定下一步。查看详情不是另起一个新的委派，也不会自动把子任务所有中间文本当主回复展示。
## message | 给同一个子智能体补充要求
已有调查只少一个条件时，告诉主任务「继续给刚才查配置的子智能体补充：也要指出测试文件」。让它使用已有 agentId 发送消息，而非再创建一个同名子任务。

核对接收者和补充后的结果。子智能体 ID 用来联系接收者，不要用某条工具调用的 ID 或旧任务里相似的标题代替。
## stop | 只停止一个子任务
展开状态列表，确认要停的是哪个子任务，要求主任务按对应的后台任务 ID 停止它。查看这一项的终态，再核对其他作业仍在运行。

主输入框的停止按钮针对前台回复，不是任意子项的停止开关。已完成的子任务无需再停；也不要拿其他会话的 ID 操作。
## create | 创建项目专用的子智能体
在对应项目打开 **设置 → 子智能体 → 新建**。选项目范围，给它稳定名称，如 `docs-reviewer`；描述写「需要逐条核对文档示例时使用」，系统提示词写「输出不匹配的命令、文件和行」。保存。

在项目的新任务里检查候选，再给它一个小问题验证。描述帮助选择角色，提示词指导接手后的工作，两栏不要只重复同一个名字。
## tools | 限制子智能体可用的工具
编辑角色配置，在工具选项中使用自定义可用工具，只留下工作需要的名称。例如仅做文档核对，不要给它修改文件或能绕过限制的命令执行能力。

保存后在新的委派中验证实际工具。提示词里的“只读”只是要求，不是权限控制；若还有能写盘的工具，就不能据此保证文件不被改动。
## model | 为某类子任务选择模型
在子智能体编辑页打开模型选择器，按名称搜索已配置的模型。想跟随主任务就保留继承策略；要固定使用某一模型，就显式选择后保存。

若没有目标模型，先回「设置 → 模型」检查提供商和模型开关。用新的子任务验证选择，不要在已有子任务中途改设置后期待它重新开始。

# skills | 技能
## use | 用 $ 调用一个已有技能
在输入框键入 `$` 和技能名片段，从候选选中技能，补上这次处理的对象，如「按发布检查清单检查当前项目，不修改文件」。发送前应能辨认出技能引用。

技能是一套按需读取的做法，不是点击后立即执行的脚本。观察回复是否按它要求产出了检查结果，而不是只回显技能名称。
## project | 给项目写第一份 SKILL.md
在练习项目创建 `.zpi/skills/release-check/SKILL.md`。同一文件同时保存用于发现技能的说明和实际步骤：

```md
---
name: release-check
description: 发布前检查版本和变更说明
---
读取 package.json 的版本，核对变更说明中是否有该版本；只报告缺项，不修改文件。
```

打开项目，在「设置 → 技能」刷新，用 `$release-check` 带入新任务。验证它检查的是当前项目：在有版本号但没有对应变更说明的练习目录运行，预期结果应指出缺少哪一版记录，而不是替你创建发布稿。技能正文要求只读并不会撤掉助手现有的写入权限。
## shared | 让几个项目共用同一技能
把技能目录放到用户技能位置，如 `~/.zpi/skills/release-check/SKILL.md`，而不是分别复制到每个项目。技能用到的相对引用文件跟随技能一起放好。

在两个项目分别创建任务，检索同一技能。若行为不同，先比较「设置 → 技能」里实际选中的来源，项目里的同名定义可能覆盖另一份。
## inspect | 查看实际发现的技能文件
在「设置 → 技能」点技能名称，核对来源、完整路径、状态和 `SKILL.md` 只读预览。两份技能同名时，路径比列表中的标题更可靠。

要修改正文，用编辑器打开该路径，不是在只读预览里输入。更新后新建任务再试，避免把旧任务中已注入的说明当成新文件没保存。
## missing | 技能没有出现在候选里怎么办？
核对目录结构、文件名 `SKILL.md` 和头部的名称、描述。确认当前任务绑定了正确项目，在技能设置中刷新，查看是否被停用、被同名技能覆盖或有加载诊断。

列表里已能看到时，回输入框重新输入 `$`。技能候选变化和已开始会话里保存的上下文不是同一次更新；必要时用新任务验证。

# commands | 自定义斜杠命令
## create | 把反复输入的要求做成斜杠命令
打开「设置 → 命令 → 新建」，名称填 `weekly`，描述写“整理本周工作”，提示词填「把我给的记录按完成、阻塞、下一步整理，不编造日期」。保存并启用。

在输入框键入 `/weekly`，检查候选、选中后发送一段练习记录。它展开的是给助手的提示，不是右侧终端的可执行程序。
## args | 给同一个命令传入不同参数
编辑命令，在提示词里用 `$1` 引用第一个位置参数，用 `$ARGUMENTS` 引用整段参数。例如模板「解释 $1；完整要求：$ARGUMENTS」，调用 `/explain note.txt 只谈第一段`。

先用不涉及写文件的模板试一次，看模型处理的文件是否正确。参数提示只是向人展示怎样填写，真正使用参数的是模板里的占位符。
## scope | 只在当前项目提供一个命令
从目标项目打开命令设置，新建命令时把作用域设为项目。用专属名称，例如 `invoice-check`，填写仅适用于该项目的路径规则，再保存。

用这个项目的新任务查 `/invoice-check`，然后到另一项目对照。如果希望所有项目共享，应该创建全局命令，而不是到处复制相同文件。
## import | 导入已有命令：选复制还是软链接
从命令设置的更多菜单点 **导入**，选择发现的命令、目标范围和导入方式。「复制」保留一份独立内容；「软链」跟随原文件以后的变化，需要原路径一直可用。

先导入一项，阅读导入结果里的已导入、跳过或失败，回设置刷新并检查候选。不了解外部命令时先读提示词和可能运行的命令段。
## linked | 编辑导入的命令会写到哪里？
先看命令路径和当初的导入方式。如果是软链接，编辑前仔细看确认框：写入可能修改原工具也在使用的那份文件，而不只影响 ZPI。

若只想试一个变化，不修改原来的公共命令，用复制方式导入独立副本或新建不同名称。保存后在目标项目用一个无副作用的例子验证。

# memory | 记忆
## short | 让新任务记住一条个人偏好
在「设置 → 记忆」启用 **短记忆**。在新任务里明确说「请记住：给我写版本说明时先列用户可见变化」。不必把密钥、临时进度或整段对话交给记忆。

到用户记忆查看是否记录了这条约定，再开另一个任务，直接说「根据这两项修改写版本说明：修好了导出，更新了内部日志」。不要在验证问题里重复“先列用户可见变化”，否则即使没有记忆也能得到相同答复。当前对话里能复述刚说过的话，并不能证明跨任务保存成功。
## project | 只让一个项目记住约定
从目标项目新建任务，明确说「请只为这个项目记住：安装依赖使用 pnpm」。在设置的**当前项目记忆**而不是用户记忆中核对它。

随后分别在该项目和另一项目开新任务验证。若是应当提交给团队的工程规范，更适合写进[项目指令](../instructions/rules.html)，不依赖某个用户的记忆设置。
## correct | 更正或移除一条短记忆
打开「设置 → 记忆」，先选用户记忆或当前项目记忆，点 **查看** 找到原条目，再用 **编辑** 修改或移除；也可以明确要求主助手更正指定约定。

每份短记忆最多 20 条，正文合计不超过 2,000 个 Unicode 字符。满了先合并重复偏好，不要删掉别的项目规则来腾位置。改完后核对文件内容，再在新任务试一次。只关短记忆开关会保留数据；它不是“忘掉某一条”的操作。
## verify | 判断记忆什么时候生效
在启用短记忆的新任务里记下一个明确约定；确认文件出现这条记录后，另开一个新任务再问。对照同一项目、同一记忆范围与首次发送时的开关。

已有任务保持当时的配置和注入内容。若新任务也没读到，先查看设置有无“文件异常，未自动加载”，不要靠重复发送同一条偏好排错。
## long | 从历史会话提取长期记忆
要复用多次工作积累的经验时，在记忆页选 **长期记忆**。它和短记忆互斥，启用其一会关闭另一种模式，不是两个摘要一直叠加。

点 **立即检查更新**，查看状态；只处理符合空闲门槛的历史，所以“没有新增内容”不等于故障。生成后从「查看长期记忆」读摘要，详情按需读取。
## model | 选择生成长期记忆的模型
在长期记忆的模型策略里选择跟随既有策略或手动指定。手动模式先选可用模型；需要分别控制提取和整合时再展开高级设置。

选择的是生成记忆的模型，不是当前对话的回答模型。检查提供商凭据和用量，再对有合格历史的一次更新验证，不要反复触发收费查询。
## pause | 暂停自动生成，不删除已有记忆
想暂时停止后台整理时，关闭长期记忆里的 **自动生成**。这会取消后台生成任务，但已生成的记忆仍可使用；无需为了暂停而清空数据。

检查状态显示暂停后再回到工作区。如果想改变后续新任务是否读取长期记忆，才需要操作长期记忆总开关。
## clear | 清空长期记忆前核对删除范围
点 **清空长期记忆…** 后先读确认：会取消相关后台任务并删除长期记忆，无法撤销；原始会话和短记忆保留。拿不准时取消，先打开长期记忆查看。

只是觉得最近更新不合适，可先暂停自动生成并保留数据。不要把“暂时不用”换成不可恢复的清空操作。

# instructions | 项目指令与系统提示词
## init | 用 /init 建立项目说明
选定项目后，在已启用项目初始化插件的新任务里输入 `/init`。它会检查工程并创建或维护**项目根目录**的 `AGENTS.md`，不是帮你生成整套新应用。

完成后打开差异，逐条确认构建命令、测试方式和限制确实来自本项目；已有规则不应被整份替换。候选里没有 `/init`，先检查插件。
## rules | 给团队写一条项目专属规则
在项目根目录的 `AGENTS.md` 写可验证的约定，如「修改表格解析后运行 `npm test`，不要改历史样本」。避免写账号、临时进度或“尽量做好”这类无法检查的要求。

在同一项目的新任务里验证约定被采用，再决定是否提交给团队。用户级指令影响多个项目，不适合记录某一仓库专用路径。
## prompt | 查看基础系统提示词
打开 **设置 → 系统提示词**，在「基础系统提示词」查看预览，并注意帮助里注明的预览目录。项目任务还会使用实际绑定目录的项目指令。

页面是只读说明，不是通用提示词编辑器。想改项目规则去改项目文件；想追溯额外行为规则，看同页的「追加指令」。
## appended | 找出追加指令来自哪个插件
在系统提示词页对照基础内容和追加内容，再到「设置 → 插件」看当前启用的条目。例如文件链接格式、交互方式和主动推进都可来自行为插件。

要验证某条规则的出处，只调整相关插件，然后开新任务对比。不要在同一次实验里同时改项目说明、记忆和模型。

# plugins | 插件
## builtins | 查看哪些内置能力已经启用
打开「设置 → 插件」，区分已安装插件与内置插件。逐项看名称、说明和开关：有的增加工具，有的只追加行为说明，因此工具数量不会随每个开关一起变化。

只想让助手改一个本地文件，不必因此开启搜索、委派和后台命令。遇到确实需要的能力，再按对应章节启用。
## toggle | 在新任务里验证一个开关
记下原来状态，一次只改一个插件，例如向用户提问。创建新任务，再到相应工具列表或任务活动核对能力；没有实际需要时模型不一定主动调用工具。

验证后可以恢复原设置。新开的能力不会把已结束的历史工具记录补出来，关闭也不会改写旧消息。
## install | 添加一个外部插件
在已安装插件区点 **添加 → 从本地文件夹添加**，选择可信的插件目录。先核对目录里的命令、技能和自动化配置，再刷新列表、检查启用状态；这里不是输入包名从市场下载。

先在练习目录的新任务验证，不要用私有项目测试来历不明的插件。外部插件不是一段只读聊天文本，不能仅凭名字判断能做什么。
## snapshot | 为什么旧对话还是原来的配置？
任务首次发送时会固定当时的插件配置；同一任务的后续消息不会自动换成另一套工具与提示。设置页看到的全局开关和旧任务看到的配置因此可能不同。

用同一项目、同一模型创建一个全新任务再比较。若新任务也缺工具，检查其他前提，例如搜索服务是否启用并有凭据。

# hooks | 钩子
## first | 在一个事件发生时自动执行命令
打开「设置 → 钩子」，新建一个项目范围的钩子，选择目标事件和运行方式。第一次用不改文件的命令，如输出一行说明，而不是拿删除或部署命令试配置。

保存后回到该项目，以一个能触发所选事件的新任务验证。钩子是事件触发的动作，不需要用户在输入框里手打斜杠命令。
## match | 让钩子只响应特定工具
选支持匹配器的工具事件，在匹配器输入正则，例如 `^edit$` 只匹配该工具名。保存后用一次读取和一次编辑做对照，只有后者应触发。

留空表示匹配全部；并非所有事件都有匹配字段。正则无效时先看表单错误，不要为了保存就去掉所有限制。
## process | 直接运行进程时怎样传参数？
在运行方式选择「进程」，命令栏只放可执行程序，参数栏**每行一个参数**。路径带空格仍放在同一行，不要人为再加一层 Shell 引号。

需要 Shell 的管道或重定向才选择「命令」。用能打印参数的练习程序检查分词是否正确，再接入实际工作流。
## scope | 把钩子限制在一个项目
打开目标项目的钩子设置，在范围中选择项目，保存后核对列表的来源。适用于只对这一仓库有意义的检查，不应让别的任务也执行它。

在另一个练习项目开启同类任务作为对照；若也触发，检查是否还存在一份同事件的全局钩子。
## diagnose | 钩子不执行，或执行到一半超时
按顺序核对：范围是否正确、事件是否发生、匹配器是否命中、程序是否可执行。若收到超时，查看高级设置中的秒数，并先在相同目录单独验证命令。

超时或任务取消会停止命令，不保证回滚它已经写的文件。排查时用无副作用的输入，不要无限调高超时来掩盖程序等待交互的问题。
